轮子 3 · 索引分层

轮子 3 · 索引分层

一个真实的失败

轮子 2 的 note 已经能存能读了。你为了测试，写了个脚本往里面灌了 50 万条笔记（每条一百多字）。然后再跑 ./build/note list：

real    0m4.213s

你以为是磁盘慢，time 了一下 cat notes.bin > /dev/null——0.05 秒。快得很。

真相是：程序在启动时把 50 万条完整记录全读进了内存，list 只是把内存里的东西打出来。你看了一眼 top，常驻内存 380 MB。你在笔记本上跑的时候，还 OOM 过一次。

问题是：你 99% 的时间只查一条笔记，却每次都要把 50 万条全部搬进内存。 这就是这一轮要拆掉的东西。数据留在磁盘上，内存里只放「去哪儿找」这张地图。

竞赛生映射

你已经会的：

  • 二分查找、哈希表。这一轮的核心还是它们，一行都没变
  • 「按 id 排序之后二分」这个套路，你在做离散化、做区间查询时用过无数次
  • 定长数组的随机访问：a[i] 是 O(1)，因为地址能算出来

真正的新东西只有一个，但它会改变你写代码的手感：

数据不在内存里，每一次访问都是 IO。

a[i] 和「seek 到第 i 条再读 128 字节」在算法复杂度上是同一件事（都是 O(1)），但代价差四到五个数量级。内存随机访问约 100 纳秒，磁盘随机读约 100 微秒。这意味着：以前可以随手做的 100 次访问，现在必须想办法合并成 1 次。 LSM 里所有看起来奇怪的设计（SSTable 按块组织、块内有序、Bloom filter），都是在为这一条让路。

你要做的东西

把 note 从「全量加载」改成「磁盘存数据 + 内存存地图」。分两步走，不要一步到位。

第一步：稠密索引

两个文件：

  • data.bin —— 只追加，一条记录一段：[长度 u32][正文]。记录本身按写入顺序排列，不排序
  • index.bin —— 定长条目，每条 16 字节：[id u64][offset u64]。按 id 升序排列

启动时只读 index.bin（50 万条 × 16 字节 = 8 MB），不碰 data.bin。查一条：在内存里对索引二分找到 offset，seekg(offset) 到 data.bin 对应位置，读长度、读正文，结束。

到这一步，启动应该已经进入百毫秒级。但你还会发现一个问题：索引本身还是线性的，8 MB 换 50 万条，500 万条就是 80 MB。所以还有第二步。

第二步：稀疏索引（真正的「分层」）

不要给每个 id 都记一条，只给每 64 条记一个锚点：[id u64][offset u64]，锚点之间隔着 64 条连续记录。

查 id 的时候：二分找到「最后一个 id ≤ 目标 id」的锚点，从它指向的 offset 开始，顺序扫最多 64 条。

代价：多扫 64 条。收益：索引内存变成 1/64。50 万条的索引从 8 MB 降到 125 KB，而且这个斜率是数据量的 1/64 —— 数据翻 10 倍，索引只多 1.2 MB。

这就是分层索引。LSM 的 SSTable 用的是同一套思路（块内有序 + 稀疏块索引），只是它的块大小按 4 KB 对齐，还多了一层 Bloom filter 用来跳过「肯定不存在」的查询。

两个必须想清楚的设计点

offset 用什么类型。 uint32_t 最大 4 GB，数据文件超过 4 GB 的那天你就会读到错误的位置，而且不会报错 —— 你会读到一段看似合法其实是别的记录的字节。用 uint64_t。这个坑 LSM 里也会有（SSTable 的 block offset），别提前踩。

改了数据，索引要跟着改。 追加一条记录 → data.bin 末尾多一段、index.bin 多一个锚点（或者改最后一个锚点的区间）；删除一条 → 数据文件不动（追加是唯一写模式），只在索引里标记为已删，或者单独维护一个删除标记文件。不要用「原地覆盖某条记录」的方式改数据 —— 变长记录原地覆盖会挤掉后面的内容，这是这一轮最容易写出的静默错误。

完成标志

用 50 万条数据测，数字要自己量出来，不要凭感觉：

  1. 启动到能接受命令 < 100 ms（time ./build/note list | head -1，或者程序里打时间戳）
  2. 单条点查 < 10 ms（time ./build/note search <某个真实存在的 id>）
  3. 内存不随数据量线性涨：分别在 10 万条和 50 万条下 top / /usr/bin/time -v 看 RSS。数据涨 5 倍，RSS 涨幅应该远小于 5 倍（稀疏索引下大概只多几百 KB）。如果你的 RSS 也涨了 5 倍，说明你还在读全量
  4. 查一个不存在的 id，能在 10 ms 内返回「没有」，不是扫全表
  5. ls -l data.bin index.bin：data.bin 是几十 MB，index.bin 是几百 KB。如果 index.bin 和 data.bin 差不多大，说明你把正文也写进索引了

常见卡点

启动还是几秒，RSS 还是几百 MB → 你只把「索引」改成了从文件读，但读的时候 while 循环里顺手把每条记录也读了一遍（比如为了算 count 或者为了排序） → 索引文件里存足够的信息（id、offset），启动阶段完全不打开 data.bin。需要 count 就单独存一个头部字段

查到的内容是别的笔记，或者读到一半乱码 → offset 类型溢出（int32_t / uint32_t 存了超过 4 GB 的偏移），或者 offset 是相对位置但你当成绝对位置用了 → offset 全用 uint64_t；seekg 一律用绝对位置（std::ios::beg）。怀疑时把 offset 和文件大小打印出来比一下

删了一条之后，再查就错位 → 在原地覆盖了变长记录，后面的数据全被挤乱 → 数据文件只追加，不原地改。删除用逻辑删除（索引里标记），或者在压缩（compact）时整体重写一个新文件再 rename

二分找得到 id，但读出来的正文和 id 对不上 → 索引排序了，数据文件没按同样顺序排（或者是按 id 二分，但数据是按写入时间追加的） → 二分的 key 和 offset 指向的记录必须严格对应。稠密索引用 id 排序、offset 指真实位置就行；稀疏索引要求锚点之间的记录也按 id 有序，否则「扫 64 条」根本扫不到

数据文件越写越大，删了也不变小 → 追加 + 逻辑删除的必然结果 → 这是特性不是 bug。压缩（compact）是 LSM 阶段 3 的内容；这一轮只需要你知道「为什么会有 compact」

对应 OJ 练习

  1. 二分查找（带不存在判定）：标准二分，但要求返回「第一个 ≥ x 的位置」和「是否存在」两个信息。稀疏索引就是靠这个定位锚点区间的。
  2. 跳表：实现 insert / find / erase，要求 O(log n) 期望。跳表是 LSM 里 MemTable 的常见实现（比平衡树好写，迭代器方向天然有序），你现在的链表 + 随机层数就能写。
  3. 静态区间第 K 小 / 有序数组离线查询：练「在有序结构上做定位」，和稀疏索引的定位逻辑同构。

HydroOJ 上搜「二分」「跳表」「有序表」；没有题库就自测：造 10 万条随机 id 的索引文件，随机查 1 万个点，和 std::lower_bound 的结果逐个比对，全一致才算过。
