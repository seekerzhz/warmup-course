轮子 4 · 日志恢复

轮子 4 · 日志恢复

一个真实的失败

轮子 3 的 note 现在又快又省内存。你写了个压测脚本，循环 1000 次 note add，每行都打印 added id=N。跑到第 963 条的时候，你等不及了，Ctrl+C……没反应（因为子进程在跑），于是 kill -9 <pid>。

重启，list | wc -l 得到 926。

少了 37 条。而且少掉的那 37 条里，有一部分是程序已经打印过 added id=N 的 —— 也就是说，程序对用户说了「存好了」，但实际上没存。

这是整个热身站里最重要的一轮。前三个轮子解决的是「数据在不在」，这一轮解决的是「程序说数据在，它就必须在」。这条承诺一旦破了，上面所有东西都没有意义 —— 一个会撒谎的数据库比一个会崩溃的数据库更危险。

竞赛生映射

诚实地说：这一轮几乎没有可迁移的东西。

你在竞赛里写的程序，要么跑完输出答案然后正常退出，要么超时被杀 —— 而超时被杀的那次提交本来就不算数。你从来不需要考虑「进程在任意一条指令处死掉之后，磁盘上留下了什么」。

这一轮是真正的新世界。但也正因为如此，它的失败场景特别具体、特别容易复现：一个 kill -9、一个 wc -l，差距就摆在那里，骗不了自己。

真正要建立的新直觉只有一条：

你写下去的字节，按「到达哪里」分三个层次，每一层的存活能力差一个数量级。

  1. C++ 流缓冲区（用户态）：进程一死就没了。ofstream::flush() 只保证数据离开这一层
  2. 操作系统页缓存（内核态）：进程死了它还在，但机器断电/内核 panic 就没了。write() 返回成功只保证到这一层
  3. 磁盘（持久）：fsync() 返回之后才算到这一层

所以「程序打印了 added」和「数据在盘上」之间，隔着一个 fsync。你没调它，就什么都没保证。

你要做的东西

给 note 加预写日志（write-ahead log，WAL）：先写日志并落盘，再改数据文件。

日志长什么样

只追加，一条记录一段：

[crc32 u32][长度 u32][操作类型 u8][payload]
  • crc32 覆盖它后面的所有字节（长度 + 类型 + payload）。校验不过 = 这条记录是坏尾，直接丢弃
  • 长度 让你能跳过不认识的记录（未来加新操作类型时不至于读崩）
  • 落盘顺序：写完整条 → fsync → 返回成功给用户

恢复流程

启动时：从头扫日志，逐条读、逐条校验 CRC。

  • CRC 通过 → 重放这条操作（幂等，见下）
  • CRC 不过，或者长度字段大到不合理（比如 > 64 MB）→ 认为这是崩溃瞬间写了一半的尾巴，停止扫描，把日志截断到上一个完整记录的末尾
  • 扫描结束后，数据文件已经追平日志，可以清空日志（或者记录一个 checkpoint 位置）

幂等的关键

重放必须能重复执行而结果不变。做法很简单：日志里记的是「目标状态」而不是「增量操作」。比如不要记 count++，要记 id=963, content="..."；重放时按 id 覆盖写，跑十遍结果一样。

如果日志里必须记增量（比如「删除 id=7」），那就得配一个「已经应用到哪个日志位置」的 checkpoint，否则第二次重放会把已经重新插入的数据又删一遍。

真正的新东西

1. flush 不等于 fsync

#include <unistd.h>
#include <fcntl.h>

int fd = ::open("wal.log", O_WRONLY | O_CREAT | O_APPEND, 0644);
// ... ::write(fd, buf, len) 之后：
if (::fsync(fd) != 0) { /* 落盘失败，必须让用户知道 */ }
::close(fd);

std::ofstream::flush() 把数据从 C++ 缓冲区推到内核，仅此而已。要真的落盘，必须拿到文件描述符调 fsync。C++ 标准库没有直接的 fsync，要么用 POSIX 的 open/write/fsync 写日志（推荐，日志路径别用 iostream），要么 fileno() 从一个已打开的 FILE* 拿到 fd。

顺便：新建文件之后，还要 fsync 它所在的目录，否则文件本身可能还没在目录项里落盘。这条很少有人提，但崩溃测试里会咬人。

2. fsync 很贵，所以要批量

一次 fsync 在 SSD 上几毫秒，在云盘上可能十几毫秒。每条记录都 fsync，1000 条就是十几秒。真实数据库的做法是组提交（group commit）：把这一小段时间内攒下的多条记录一次 write + 一次 fsync，然后一起返回成功。

代价是延迟变高（要等攒批），收益是吞吐量翻几十倍。这一轮你先做「每条 fsync」的正确版本，跑通之后再考虑攒批 —— 正确性优先。

3. 崩溃发生在任意位置，包括「写了一半」

kill -9 可以在 write 执行到一半的时候到达（内核层面可能只写进去一部分字节）。所以日志尾部出现「长度字段说 200 字节，实际只跟了 80 字节」是正常现象，不是异常。恢复逻辑必须把它当成正常情况处理：丢掉这条，把文件截断到它的起点。

这也是为什么每条记录都要带 CRC 和长度：没有它们，你无法区分「写了一半的记录」和「一条内容恰好很短的合法记录」。

完成标志

  1. 写 1000 条 → kill -9 进程 → 重启 → list | wc -l 等于 1000，一条不少
  2. 能主动复现「不 fsync 就丢数据」：把 fsync 那行注释掉，同样的 1000 条 + kill -9，重启后的条数小于 1000。这个对比你必须亲眼看到一次
  3. 手工截断日志：truncate -s -50 wal.log 砍掉尾部 50 字节，重启，程序能识别出坏尾、跳过它、正常启动，并且不丢之前的记录
  4. 幂等：把恢复流程连续跑两次（第二次日志已经清空，或者用 checkpooint 位置），数据条数不变，不是 2000
  5. 被截断的那部分字节，日志文件大小要真的变小（说明你做了 truncate，而不是只在内存里跳过）

常见卡点

以为 ofstream::flush() 就是落盘 → 这是最常见的误解，也是最贵的 → 换成 open/write/fsync。验证方法：写完立即 kill -9，看数据在不在。flush 版本会丢，fsync 版本不丢

kill -9 之后一条都没丢，怀疑自己写错了 → 内核页缓存还没来得及回写，但进程死了之后页缓存仍然有效，几秒内数据就落到盘上了；而且你没断电，只是进程死了 → 要看到「不 fsync 也丢」的现象，得在写入刚返回的瞬间杀进程，或者用 echo 3 > /proc/sys/vm/drop_caches 之类的手段。更可靠的做法：把写入循环调慢（每条后面 sleep 1ms），在循环中途杀

重放之后数据翻倍，或者删除的记录又回来了 → 重放不幂等，或者重复重放了同一段日志 → 日志里记「目标状态」，或者维护 checkpoint（已应用到哪个偏移），恢复时从 checkpoint 之后开始

CRC 总是不匹配，明明数据是对的 → CRC 覆盖范围算错了（比如把 crc 字段自身也算进去了），或者写入方和读取方对「哪些字节参与计算」理解不一致 → 明确约定：CRC 只覆盖它后面的字节。写的时候先留空 4 字节，算完再回填

日志文件无限增长，几 GB → 没有 checkpoint / 清理机制 → 每次数据文件追平日志之后，记录 checkpoint 位置；日志超过阈值就整体重写（只保留 checkpoint 之后的部分）

fsync 之后仍然丢数据（极少见但发生过） → 云盘/虚拟机的写缓存策略；或者文件首次创建时目录项没落盘 → 创建文件后 fsync 目录；测试环境用 fsync 语义可靠的本地盘

对应 OJ 练习

  1. CRC32：实现标准 CRC32（多项式 0xEDB88320，反射算法），和 zlib 的结果对比。这是日志校验的核心，也是 LSM 里每个 block 都在用的东西。
  2. 带长度前缀的流式解析：给一段可能被截断的字节流，输出「能完整解析多少条记录」和「最后一条的起始偏移」。这就是恢复流程的核心逻辑。
  3. 模拟幂等重放：给定一条操作日志和一个初始状态，要求「重放第 i 次」和「重放第 j 次」得到相同结果。用纯函数写，很好测。

HydroOJ 上搜「CRC」「模拟」「字符串处理」；没有题库就自测：自己构造 3 组日志（完整 / 尾部截断 / 中间 CRC 坏），恢复结果必须分别是「全部重放」「重放到坏尾前」「拒绝并报错」。
