轮子 5 · 并发与优雅关闭（选做）

轮子 5 · 并发与优雅关闭（选做）

一个真实的失败

轮子 4 之后，你的 note 已经是一个说得过去的存储程序了。你想加一个「后台整理」：磁盘上的数据文件越写越大，让一个后台线程定期把已删除的记录真正挤掉，重写一个新文件。

你起了 std::thread，它每 5 秒扫一遍。前台 note add 照常工作。看起来挺好。

然后你按了 Ctrl+C：

terminate called without an active exception
Aborted (core dumped)

因为主线程 return 0 的时候，那个后台线程还在跑。std::thread 析构时如果线程仍 joinable，标准规定直接 std::terminate —— 不是「等它跑完」，是当场杀掉整个进程。

更阴险的一种：如果你不 Ctrl+C，让后台线程在整理的同时前台在 add，偶尔会读到半条记录 —— 因为后台正在重写文件，前台正好 seek 到了那个位置。这种 bug 一百次跑不出一次，出了就是数据损坏。

竞赛生映射

可迁移的：一个数据结构被两方同时改这件事本身，你在并查集、线段树 lazy 标记里都处理过「状态要一致」。思路是一样的：先想清楚「哪些操作必须原子地一起完成」。

全新的东西是三件，而且都是工程性的、不是算法性的：

  1. std::thread 的生命周期规则（必须 join 或 detach，否则析构就 terminate）
  2. mutex / 条件变量 / 读写锁的用法，以及它们不保证什么（不保证公平，不保证唤醒）
  3. 信号（SIGTERM）的处理只能在极其受限的环境里做

你要做的东西

给 note 加一个后台整理线程，并让整个程序能被 SIGTERM 干净地关掉。三件事：

1. 后台线程

每 5 秒检查一次数据文件：如果「已删除记录」占比超过 30%，就把存活记录重写到一个新文件，然后 rename 覆盖。

重写期间不能挡住前台写。做法不是「加一把大锁」，而是写时复制 + 原子改名：新文件写完之后 rename，前台拿到的是旧文件句柄或新文件句柄，不会拿到半个。

2. 读写锁

shared_mutex：多个读者可以同时持有，写者独占。

  • 前台 search / list → 共享锁（读锁）
  • 前台 add / delete → 独占锁（写锁）
  • 后台整理的文件切换 → 独占锁，但只在切换那一刻加，重写过程本身不加

用反了（读操作加写锁）不会崩，只是并发能力归零，你会看到「后台整理时前台完全卡死」。

3. 优雅关闭

收到 SIGTERM（或 SIGINT）之后，线程要能自己收尾：把手上这一批做完、fsync、退出循环、join 回来、然后进程正常返回。

关键设计：信号处理函数里不要做任何事，只置一个标志。 信号处理函数运行在极受限的环境里，printf、malloc、锁都可能死锁。

#include <atomic>
#include <csignal>
#include <thread>

std::atomic<bool> g_stop{false};
extern "C" void on_signal(int) { g_stop.store(true); }   // 只做这一件事

// 在别的线程里 cv.wait_for(..., []{ return g_stop.load(); })
// 主线程解析 signal(SIGTERM, on_signal) 之后，join 后台线程

std::atomic<bool> 在信号处理函数里是安全的（无锁、无分配）。别用普通 bool，编译器可能会把它优化进寄存器，导致主循环永远看不到变化。

真正的新东西

1. mutex 就这五行

#include <mutex>
std::mutex m;

{
    std::lock_guard<std::mutex> lk(m);   // 构造即加锁，析构即解锁
    // 临界区
}                                        // 出了作用域必定解锁，异常也解锁

lock_guard 是 RAII（资源获取即初始化）的最小例子：把「必须成对出现的操作」绑在对象的生命周期上，就不可能忘。这是 C++ 工程里最重要的一条习惯，比任何算法都值钱。

要「多个读者并行、写者独占」，把 std::mutex 换成 std::shared_mutex，读用 std::shared_lock，写用 std::unique_lock。

2. 条件变量必须配循环

std::unique_lock<std::mutex> lk(m);
cv.wait(lk, []{ return has_work() || g_stop.load(); });   // 带谓词的版本，内部就是循环

条件变量会有虚假唤醒（没通知它也返回了），也会丢失唤醒（通知在 wait 之前发出）。所以判断条件必须放在循环里。带谓词的 wait 帮你写了循环，用它，别手写裸 wait。

3. -fsanitize=thread 是你的裁判

cmake -S . -B build-tsan -DCMAKE_CXX_FLAGS="-fsanitize=thread -g -O1"
cmake --build build-tsan -j
./build-tsan/note add "test"

TSan 会在真的发生数据竞争时打印两处调用栈。它只报实际执行到的竞争，所以要把并发路径都跑一遍（前台读 + 后台写，同时进行）。干净的 TSan 输出是这一轮唯一的客观标准 —— 不要用「我看了代码觉得没问题」代替它。

完成标志

  1. 后台整理时前台读不阻塞：让后台开始整理大文件，同时前台连续 search 100 次，总耗时和「没有后台整理时」相差不超过 2 倍
  2. TSan 干净：-fsanitize=thread 编译，跑一遍「前台 1000 次读写 + 后台整理」，零警告
  3. SIGTERM 后干净退出：kill <pid> 之后进程退出码正常（不是 134/abort），没有 terminate called，日志里没有半条记录
  4. SIGTERM 期间数据不丢：正在写的记录要么完整写进日志，要么完全没写，不出现半条
  5. 重复 SIGTERM 不出事：连按两次 Ctrl+C，第二次不会让程序崩在信号处理里

常见卡点

退出时 terminate called without an active exception → 线程还 joinable，std::thread 对象被析构了 → 所有线程都要有明确的归宿：要么在某处 join()，要么在启动后立刻 detach()。存储程序里优先 join()

cv.wait 之后条件还是不满足，或者线程永远不醒 → 忘了循环判断（虚假唤醒），或者通知在 wait 之前就发了（丢失唤醒），或者通知时没持锁/条件变量和 mutex 不是配对的 → 用带谓词的 wait(lk, pred)；修改条件时持锁，改完再 notify_one/all

加了并发之后反而更慢，串行化严重 → 读写锁用反了（读操作拿了写锁），或者临界区太大（把 IO 也包在锁里） → 读路径用 shared_lock；把「读文件内容」挪到锁外，锁里只保护元数据

kill 之后进程不动，卡住不退 → 信号被某个线程屏蔽了，或者后台线程在 wait 里没检查停止标志 → 检查 wait 的谓词里有没有 g_stop；确认 signal() 在主线程、任何线程启动之前就注册好

TSan 报竞争，但你确信那两行不会同时执行 → 通常是真的：其中一个访问没有加锁，或者锁保护的粒度不一致（一边锁了 m，另一边锁了 m2） → 看 TSan 给的两处栈，找到它们各自持有的锁，对比是不是同一把

在信号处理函数里打印，偶尔死锁 → 信号处理函数不能调用 printf / malloc / 任何非 async-signal-safe 的函数 → 处理函数里只置 atomic<bool>，真正的收尾逻辑放在主循环里

对应 OJ 练习

并发本身不适合 OJ（判题机不稳定），但有两块纯逻辑非常值得刷：

  1. 无锁计数器 / 单生产者单消费者队列：先写一个有锁版本，再写一个 atomic 版本，用压力测试对比。重点是理解 memory_order 的 relaxed / acquire / release 分别在保证什么。
  2. Bloom filter：位数组 + 多个哈希，判「可能存在 / 一定不存在」。它是 LSM 里减少无效 IO 的关键结构，纯函数、易测，适合 OJ 化。

HydroOJ 上搜「位运算」「哈希」「模拟」；没有题库就自测：给定 10 万次插入和 10 万次查询，要求误判率 < 1%、无假阴性，内存占用 < 1 MB。
