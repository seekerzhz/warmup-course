轮子 2 · 让 note 记住

轮子 2 · 让 note 记住

一个真实的失败

轮子 1 的 note 用得很顺。你连着加了二十条笔记，list 输出整齐，search 一找一个准。然后你按了 Ctrl+D，去吃了顿饭。

回来重开程序，list 是空的。

你开始加持久化。第一版很朴素：ofstream fout("notes.txt")，每条笔记一行，getline 读回来。跑通了。第二天你想给笔记加一个创建时间，格式从 id|内容 变成 id|时间|内容。你重开程序，它读了旧文件，把「时间」字段读成了内容的一部分，然后 stoi 抛异常，程序直接崩了 —— 而且崩在读取阶段，你连「文件里到底有什么」都看不到。

这一轮解决两件事：数据要活过进程，以及格式要能被未来的自己改而不炸。

竞赛生映射

你已经会的：

  • 编码解码本身。把结构体压成一串字节、再从字节还原，本质就是位运算加字符串处理，你在压缩、哈希、状态压缩里干过很多次
  • 定长记录 vs 变长记录的区别，你在处理输入格式时天天遇到

真正的新东西：

  1. 文件是有状态的资源。打开、读、写、关闭，每一步都可能失败，失败了要么处理要么退出，不能假装没发生
  2. 格式是给未来的自己看的一份合同。今天写的文件，三个月后还要能读。所以要有版本号，要有校验，要能识别「这不是我的文件」

你要做的东西

给 note 加 save / load，数据存在 notes.bin。启动时自动 load，每次修改后自动 save。

先写文本格式，跑通；然后换成二进制格式，跑通；最后给二进制格式加版本号和损坏检测。顺序不要跳，文本版是你理解「字段边界在哪」的最快方式。

一个能活过改版的格式，至少要有这四段（顺序随意，但必须都有）：

段 作用 不加会怎样
magic（4–8 字节固定串） 认亲：这到底是不是我的文件 拿到一个随便什么文件也当笔记读，读出一堆垃圾
version（整数） 告诉读取方按哪套规则解析 加字段的那天，旧文件全部解析错位
count（记录条数） 预分配、循环边界 只能靠猜结尾，最后一个坏字节就导致死循环
每条记录 id、长度、正文 ——

正文是变长的，所以记录里必须显式存长度。不要存 sizeof(std::string) —— 那是一个固定的小数值（通常是 32），跟正文长度毫无关系。这是这一轮最高频的翻车点。

真正的新东西

1. 二进制 IO 就这几行

#include <fstream>

// 写
{
    std::ofstream out("notes.bin", std::ios::binary | std::ios::trunc);
    uint32_t n = 42;
    out.write(reinterpret_cast<const char*>(&n), sizeof(n));
    // 出了作用域自动 close，close 会 flush
}

// 读
{
    std::ifstream in("notes.bin", std::ios::binary);
    if (!in) { /* 文件不存在或没权限，必须处理 */ }
    uint32_t n = 0;
    in.read(reinterpret_cast<char*>(&n), sizeof(n));
    if (!in) { /* 读失败：文件被截断了，或者根本不是这个格式 */ }
}

三个关键点：std::ios::binary 必须加（不加的话 Windows 上会把 \n 悄悄换成 \r\n，字节数就对不上了）；read/write 的单位是字节数，不是元素个数；每次 read 之后都要检查流状态，因为「读到一半文件结束」和「读成功」在返回值上没区别。

2. 检查失败，而不是假设成功

ifstream 的对象可以直接当 bool 用。打开失败、读到一半失败、读到不该有的位置，都会让流变成 false。每一次 read 后面都必须跟一次检查，否则你会在垃圾数据上继续跑，然后在很远的地方崩掉，错误信息和真正的原因完全对不上。

3. 写入要用「临时文件 + 改名」

直接往 notes.bin 上覆盖写，如果写到一半被杀掉（下一轮你会天天干这事），文件就毁了一半：前半段是新数据，后半段是旧数据，长度字段还可能对不上。

正确做法：写 notes.bin.tmp，全部写完、close、确认没出错，再 std::filesystem::rename 覆盖 notes.bin。rename 在同一文件系统内是原子的 —— 要么是完整的旧文件，要么是完整的新文件，不存在中间态。

4. 版本号怎么用

读的时候先读 version，然后分支处理：v1 按老规则解析，v2 多读一个时间戳字段。新版本要能读旧文件；旧的程序读到新文件，应该明确报「版本太新，请升级」，而不是硬着头皮解析出一堆垃圾。

完成标志

  1. add 三条 → 退出程序 → 重新启动 → list 还是三条
  2. 用编辑器把 notes.bin 中间某个字节改掉（随便改一个数字），重新启动，程序打印一行错误并退出，不是崩溃、不是输出乱码、不是死循环
  3. 删掉 notes.bin 再启动，程序正常起来（空列表），不报错
  4. 文件头能看出 magic 和 version：xxd notes.bin | head -3 前几个字节是固定的，第 5–8 字节随版本变
  5. 把 version 手动改成 99，程序报「不支持的版本」而不是崩

常见卡点

读回来内容对不上，后面全部错位，或者读出乱码 → ofstream / ifstream 没加 std::ios::binary，或者读写时 sizeof 的对象不一致（写 uint32_t 读 size_t，64 位下前者 4 字节后者 8 字节） → 读写用同一套类型定义（都用 uint32_t），并且两端都显式写 std::ios::binary

写进去的字符串读回来只有一两个字符，或者是乱码 → 用了 write(&s, sizeof(s))，存的是 std::string 对象本身（指针 + 长度 + 容量），不是正文 → 存 s.size() 再存 s.data()，读的时候先读长度、resize 之后再 read 到 &s[0]

最后一条记录丢了，或者程序读完就崩 → close / flush 没做，数据还在用户态缓冲区里进程就退出了；或者循环边界用了 count 但文件里实际少于 count 条 → 确保 ofstream 出了作用域（或显式 close()）；读取循环里每次 read 都检查流状态，失败就当作文件截断并报错

改了结构体字段之后，旧文件全部读不出来 → 没有版本号，或者加了字段但没升 version → 加 version，读取时按版本分支；旧数据无条件按老格式解析

rename 报了 filesystem error → notes.bin.tmp 和目标不在同一目录/同一文件系统，或者目标文件还开着 → 临时文件放在目标同目录；改名之前确保目标文件没有打开的句柄

对应 OJ 练习

这一轮能 OJ 化的就是编码解码本身，非常适合刷：

  1. VarInt 编解码：把无符号整数按 7 位一组、最高位当续位编码成变长字节串，再解回来。写两遍：一遍正确处理，一遍故意用坏输入（截断的 VarInt）验证你的错误处理。这是 LSM 里 SSTable 索引块真正在用的编码。
  2. 定长记录文件解析：给定一段十六进制字节流，按「magic + version + count + 记录」解析并输出每条记录，遇到坏数据要输出错误行号而不是崩。
  3. CRC 校验：给一段字节算 CRC32，和标准实现对比。这是下一轮（轮子 4）日志校验的直接前置。

HydroOJ 上搜「模拟 / 字符串处理 / 进制转换」类题目都能对上；没有题库就自测：准备 3 组输入输出，其中一组必须是故意损坏的输入，程序能报错才算过。
